Turing Game UI mockups

Static 1024×768 design comps for bead tg-84y.4. They use the real tile and robot PNGs; anything still in the old style is labelled "old art". The tiles animate in phase on the shared 0.04 s clock; add ?still to a URL to freeze them. These pages are not game code.

A. Main screen: Terminal

  • Idea: the game's phosphor CRT (intro, selector, credits) becomes the UI chrome. Everything sits on greenscreen.png, with phosphor panels, pixel-font labels and a scanline glass. The Toybox board and cell glow inside it like small colour displays.
  • Hierarchy: the 8×8 CPU (54 px tiles) is the hero. RUN is the only filled control. The cell, registers and score sit in one column on the right.
  • Quintus: the background is the existing greenscreen.png. Panels are flat strokes. The scanline glass is a pre-rendered transparent PNG drawn last, or it can be dropped in canvas.

B. Main screen: Toybox desk

  • Idea: the whole screen is a cosy workbench. Cream cards with ink outlines and toy "lift" shadows sit on it. The board is a sky-blue play mat, the cell is a tomato window, and the tiles wait in a yellow tray.
  • Hierarchy: a big tomato RUN button, coloured tabs that name each area, and a level badge. The palette, outline and shadows all come from the tile art, so the chrome and the pieces read as one toy.
  • Quintus: the cards, tray, mat and window are flat rounded rectangles: either one pre-rendered background per layout, or Q.UI.Container with radius and stroke. The body text uses a rounded system font.

C. Level selector: unlock map

  • Idea: keep the green CRT charm, but draw the real required graph as circuit traces with 45° corners and vias, so the motherboard idea returns in the place it reads best.
  • Layout: the tutorial runs down the left, then conditionals splits into a Movement track (top) and an Arithmetic track (bottom), read left to right by unlock depth. Both tracks meet at an AND gate that feeds the four finale levels, which need robozzle and Fibonacci.
  • States: open levels are lit, glow and carry a ▶ marker. Solved levels show 3 part slots, filled per part earned. Locked levels are dashed and dim, and the traces into them are dashed too. Vanity, the key and the parts total are always visible. All 45 levels fit with no scrolling.
  • Quintus: replace each level's hand-set x/y with a col/row lane table and draw the traces from required. Then a new level only needs a lane.

How to build it: recommendation

Use an HTML/CSS overlay for the chrome. Keep everything you drag, rotate or animate in the Quintus canvas.

  • Canvas keeps: the board tiles, palette tiles (drag source), trash (drop target), the cell, the robot, the run dot, and the start marker. That code already works with touch through Q.touch, and it is what animates.
  • Overlay takes: the header (title and wrapped instruction text), the transport, Help and Levels, the registers, the score, the panel frames and labels, the whole level selector, and the end-level and help popups.
  • Why: these comps are already HTML/CSS, so the port is close to a copy. Text wrapping, glow, rounded cards, hover, focus and keyboard access come free; in canvas each one is hand-written. The level map stays data-driven: DOM nodes plus one SVG of traces.
  • Input: the overlay root has pointer-events:none; only its controls take events, so drags on the canvas board are untouched. The existing Q.touch(Q.SPRITE_UI,[...]) gating needs a twin, a class on the overlay that disables the buttons during playback and popups.
  • Scaling: put the canvas and the overlay in one 1024×768 stage div and scale that with a CSS transform, so both scale together. quintus_touch.js maps touches with pageX - offsetLeft, which ignores transforms: patch it to use getBoundingClientRect() and the scale factor (about 10 lines). Mouse offsetX is already transform-aware in modern browsers.
  • Scenes: each Q.scene shows and hides its overlay panel, and Q.clearStages() hides them all. That is a small glue function per scene.

Notes and findings

  • Sample state is a composite: it uses the text of De revolutionibus and a 3×3 world (robot c, obstacles, hatch), plus a red counter and red ±1 tiles so that every element appears. The real level has a 5×5 board and no counter. The program (step, turn R, step, belt, turn L, step) solves that world.
  • Board size: boards run from 1×1 to 8×8. Draw them centred in the fixed 432 px display: 54 px for 8×8, up to 100 px for small boards, preferring whole-number scales of 50.
  • World size: worlds run from 3×3 to 11×11 (12 levels use 9–11). The cell display is a fixed box of about 310–330 px. Suggested tile sizes are 100 px up to 3×3, 50 px up to 6×6, 40 px up to 8×8 (8×8 at 40 = 320 px), and 28–30 px up to 11×11. Non-integer scales should use smoothing.
  • Palette limits: no level limits how many parts you may use; the score counts parts plus steps instead. So the palette shows names, not counts, and the score panel shows the three thresholds from getResult.
  • Speed: the old "rewind" and "fast-forward" buttons are slower and faster (TuringTable.slower/faster). Here they are « and » around the speed readout.
  • Trash: the old trash button clears the whole board (TuringTable.clear). Here it is also the drop target for deleting a single tile.
  • Belt corners: belts are straight on every tile, so a turn in the program flow breaks the belt (see the corner at column 4). A belt-corner variant is a candidate follow-up for the program-tiles class.
  • Still old art: world terrain (purple floor, obstacles, hatch, trap), counter tiles, the start chevron, and the parts icons (capacitor, IC, coil). The robot uses robot-front-c-50.png.
  • Fonts: the pixel labels use the 5×7 font from tools/art/lib/font.mjs, copied into comp.js (upper case only). Body text uses system monospace (A, C) or a rounded system font (B). No web fonts or CDNs.
